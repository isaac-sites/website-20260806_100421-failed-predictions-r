## Introduction

A UFO prediction can only be tested fairly when its wording is preserved **before the promised event is due**. The essential record is not a later summary saying that someone “predicted contact”, but a dated copy showing exactly what was claimed: the deadline, location, duration, visibility, named participants and any conditions attached to success.



<figure class="article-media-figure article-media-figure-overview"><img src="{{ "/assets/images/failed_predictions_r_c5c2a1_documenting_ufo_pred_0ba123-overview.webp" | relative_url }}" alt="Overview image for Prediction Records" width="1024" height="559" loading="lazy" decoding="async" fetchpriority="low"><figcaption class="article-media-caption"><span class="article-media-caption-label">Illustrative overview</span></figcaption></figure>

Good documentation prevents two opposite errors. It stops critics from making a vague claim sound more precise than it was, and it stops a failed prediction from being softened after the deadline into something symbolic, private or conditional. The strongest record combines the original material with independent proof of when it existed: an archived webpage, circulated email, contemporary newspaper report, recording, printed notice or trusted timestamp. No single format is perfect, so important predictions should be preserved through several independent channels.

The first question is not whether a prediction later appeared to fail. It is whether there is reliable evidence that the relevant wording existed before the deadline.

## Capture the wording, not merely the theme

A weak record says, “Aliens were predicted to arrive in October.” A strong one preserves the complete statement and separates its individual commitments.

For testing purposes, the record should reproduce the claimant’s exact words and then extract the promised elements without rewriting them. Researchers should note:

* the precise date, time and time zone;
* whether the event concerns a landing, visible craft, catastrophe, rescue or official [announcement]({{ 'two-dates/' | relative_url }});

<div class="content-enhancement content-enhancement--insight-grid" markdown="1">

* the stated geographical area;
* who should be able to observe it;
* how long it should last;
* what physical or public evidence was promised;
* any stated conditions, escape clauses or acceptable delays;
* whether the claimant described the date as certain, probable or provisional.

</div>

This distinction matters because later disputes often turn on one overlooked phrase. A prediction that says a craft “will appear worldwide for three days” is materially different from one saying that unusual lights “may be noticed by receptive observers”. Both concern UFOs, but only the first offers a clear public test.

The original form should be retained wherever possible. For webpages, save the page’s URL, visible text, images and linked files. For audio or video, keep the full recording rather than a short extract, together with its title, running time, publication page and surrounding discussion. For print, photograph or scan the whole notice, including masthead, page number, date and adjacent material that helps identify the publication. Cropping away that context can make a genuine item look less reliable.

Screenshots are useful as quick visual records, but they should not stand alone. A screenshot can omit the URL, hide edits, lose embedded material or be misattributed to the wrong account. Research on social-media screenshots treats attribution as a distinct verification problem and uses handles, visible timestamps, text and archived copies to locate the original post.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://arxiv.org/abs/2510.22939" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: arxiv.org">[arXiv]</a><span class="citation-popover" role="note"><span class="citation-popover-source">arxiv.org</span><span class="citation-popover-title">arXiv Web Archives for Verifying Attribution in Twitter Screenshots</span><span class="citation-popover-snippet">Web Archives for Verifying Attribution in Twitter ScreenshotsOctober 27, 2025...</span><span class="citation-popover-meta">Published: October 27, 2025</span></span></span>

## Dates require more than one timestamp

A visible date on a blog post or message is evidence, but not conclusive evidence. Website owners may edit pages while retaining the original publication date, computers may have incorrect clocks, and a copied document can preserve text while losing its transmission history.

For that reason, the most useful chronology distinguishes at least three dates:


<div class="content-enhancement content-enhancement--insight-grid" markdown="1">

* **Claimed publication date:** the date displayed by the author or platform.
* **Independent capture or transmission date:** when an archive, mail server, broadcaster, newspaper or recipient recorded the material.
* **Prediction deadline:** when the promised event was supposed to occur.

</div>

The independent date is the crucial bridge between the claim and its deadline. A web archive capture made on 10 October can establish that a page was available no later than 10 October, even if the page itself claims to have been posted on 1 October. It does not necessarily prove that 1 October was the true publication date.

Wayback Machine records must also be read carefully. The Internet Archive warns that archived sites may be incomplete and that missing links can lead to material from another capture date or, in some circumstances, the live web. Researchers should therefore check the timestamp embedded in each archived URL rather than assuming that every element displayed on an archived page came from the same capture.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://help.archive.org/help/using-the-wayback-machine/" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: help.archive.org">[Internet Archive Help Center]</a><span class="citation-popover" role="note"><span class="citation-popover-source">help.archive.org</span><span class="citation-popover-snippet">Internet Archive Help CenterUsing the Wayback MachineWhen you are surfing an incomplete archived site the Wayback Machine will grab the c...</span></span></span>

Web archiving is selective rather than continuous. Studies of archive coverage have found substantial gaps and large differences in how frequently pages are captured. A page first archived after a failed deadline may preserve the wording, but it cannot by itself prove that the wording was present beforehand.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://arxiv.org/abs/1212.6177" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: arxiv.org">[arXiv]</a><span class="citation-popover" role="note"><span class="citation-popover-source">arxiv.org</span><span class="citation-popover-title">arXiv How Much of the Web Is Archived?</span><span class="citation-popover-snippet">How Much of the Web Is Archived?December 26, 2012...</span><span class="citation-popover-meta">Published: December 26, 2012</span></span></span>

Email can provide stronger chronological detail when the native message is retained. The full headers may contain a Message-ID and a sequence of “Received” fields showing passage through mail servers. The sender’s visible date can be inaccurate or manipulated, so it should be compared with the server-generated routing times. ## Build a small evidence package

The practical goal is not to create an elaborate forensic laboratory for every online rumour. It is to assemble a compact package that another researcher can independently inspect.

A sound preservation package should contain:

**The original object.** Save the webpage, email, audio file, video, document or high-resolution scan in its native or highest-quality available form.

**A readable copy.** Create a PDF, screenshot or transcript for convenient review, but retain the original alongside it.

**Source details.** Record the author, account name, URL, publication title, date displayed, date collected and collector’s name.

**The exact prediction.** Transcribe the relevant wording without silently correcting grammar or substituting clearer language.

**A structured claim sheet.** List the deadline, location, expected observers, promised event, duration and stated conditions.

**Independent date evidence.** Add an archive URL, received email copy, newspaper page, broadcast schedule or other dated corroboration created before the deadline.

**Integrity information.** Generate a cryptographic checksum, sometimes called a hash, for each digital file. A changed file produces a different value, making later alteration detectable. The US National Archives describes checksums as a method of verifying that preserved files have not changed and recommends retaining relevant preservation metadata with digital records.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://records-express.blogs.archives.gov/2016/11/21/metadata-in-electronic-records-management/" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: records-express.blogs.archives.gov">[Records Express]</a><span class="citation-popover" role="note"><span class="citation-popover-source">records-express.blogs.archives.gov</span><span class="citation-popover-title">Records Express Metadata in Electronic Records Management</span><span class="citation-popover-snippet">Records Express Metadata in Electronic Records Management</span></span></span>

For unusually important or disputed predictions, a trusted timestamp can strengthen the package. The Internet standard RFC 3161 defines a system in which a timestamping authority can support the assertion that particular data existed before a specified time. The service timestamps a digital representation of the material rather than relying solely on the claimant’s own clock.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://www.rfc-editor.org/info/rfc3161/" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: rfc-editor.org">[RFC Editor]</a><span class="citation-popover" role="note"><span class="citation-popover-source">rfc-editor.org</span><span class="citation-popover-snippet">Open source on rfc-editor.org.</span></span></span>

Redundancy is more valuable than technical sophistication alone. A cryptographic timestamp proves little about authorship if the wrong file was submitted; a newspaper report may abbreviate the wording; a webpage capture may omit a video. When the claimant’s page, an archived copy, a recipient’s email and an independent contemporary report all agree, the evidential position becomes much stronger.

## Preserve revisions as separate records

Prediction pages frequently change as the deadline approaches. Details may be clarified, softened or expanded; qualifications may appear only after publicity grows. Overwriting the earlier copy destroys precisely the evidence needed to understand that evolution.

Each materially different version should therefore be saved as a new item. A simple version log can record:

VersionDate first observedMaterial change13 SeptemberCraft promised on a named date29 SeptemberDuration and geographical scope added313 OctoberVisibility made conditional415 OctoberPost-event explanation published

The log should describe changes neutrally. It should not assume that every edit was deceptive: authors correct errors and answer questions. The evidential point is that a claim must be evaluated according to the version available before the deadline, not a later composite assembled from several stages.

Goodchild’s published index makes this distinction unusually visible. It identifies a final message before 14 October 2008 and then separately lists the first post-deadline message, in which disappointment and reasons for the non-appearance were discussed. Keeping that boundary intact prevents the explanation for failure from being mistaken for part of the original prediction.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://www.blossomgoodchild.com/channelling-indexes/" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: blossomgoodchild.com">[Blossom Goodchild]</a><span class="citation-popover" role="note"><span class="citation-popover-source">blossomgoodchild.com</span><span class="citation-popover-title">Blossom Goodchild Channelling Indexes &#124; Blossom Goodchild</span><span class="citation-popover-snippet">Blossom Goodchild Channelling Indexes &#124; Blossom Goodchild</span></span></span>

## Avoid retrospective reconstruction

The greatest threat to a fair assessment is often not outright fabrication but gradual reconstruction. Years later, participants may sincerely remember a prediction as more exact, more widely circulated or more conditional than the surviving record shows.

Several common practices should be avoided.

**Do not merge different statements into one prediction.** A date from one message, a location from another and a dramatic description from a third may create a claim that no single source actually made.

**Do not treat a later memoir as proof of prior wording.** Memoirs and interviews are useful accounts of what participants remember, but they are secondary evidence unless supported by contemporary documents.

**Do not infer certainty from publicity.** A headline may present a speculative statement as a firm promise. The claimant’s own wording must remain the primary reference.

**Do not add conditions after the event.** If invisibility, spiritual fulfilment, [human readiness]({{ 'human-readiness/' | relative_url }}) or government [interference]({{ 'interference/' | relative_url }}) was not stated before the deadline, it cannot retrospectively become part of the original test.

**Do not equate missing records with vindication.** Failure to locate an archived page does not prove that the prediction was never made. Web archives are incomplete. The correct conclusion is that the surviving evidence is insufficient to establish the claim with confidence.<span class="citation-link-wrap"><a class="citation-inline-link" href="https://bl.iro.bl.uk/downloads/ce6a17f4-a0e0-4501-addf-2b48d7320d86" target="_blank" rel="noopener noreferrer nofollow" aria-label="View source: bl.iro.bl.uk">[British Library]</a><span class="citation-popover" role="note"><span class="citation-popover-source">bl.iro.bl.uk</span><span class="citation-popover-snippet">Open source on bl.uk.</span></span></span>

**Do not preserve only hostile commentary.** A critic’s summary may omit qualifications just as a believer’s later account may add them. Preserve the primary statement and the criticism separately.

This discipline protects both sides of the evaluation. It prevents an alleged UFO prophet from being judged against wording they never used, while also preventing a well-documented failed promise from dissolving into a vaguer claim after nothing happens.

## A practical test for future cases

Before classifying a UFO prediction as failed, ask whether the [evidence package]({{ 'evidence-package/' | relative_url }}) permits clear answers to five questions:

1. Can the original or near-original wording be inspected?
2. Is there independent evidence that this wording existed before the deadline?
3. Does the statement promise an observable event rather than a [private experience]({{ 'private-proof/' | relative_url }})?
4. Are the deadline and success conditions sufficiently definite?
5. Have post-deadline explanations been kept separate from the prior claim?

A prediction that satisfies all five can be assessed against what actually occurred. One that fails the second question should be labelled **retrospectively reported**, not confidently documented. One that fails the third or fourth may be too elastic to test at all.

The difference is fundamental. Failed UFO predictions are meaningful evidence only when the historical record fixes the claim before reality has supplied the answer. Without that constraint, every missed landing, absent spacecraft or postponed [revelation]({{ 'revelation/' | relative_url }}) remains vulnerable to later rewriting—and the apparent failure may tell us more about memory and record-keeping than about what was originally predicted.

      link.setAttribute('href', buildUrl(query, reference, marketId));
    });
    var select = section.querySelector('[data-ebay-market-select]');
    if (select && available.indexOf(marketId) >= 0) select.value = marketId;
    var selectedText = marketId;
    if (select && select.selectedIndex >= 0) selectedText = select.options[select.selectedIndex].text;
    Array.prototype.slice.call(section.querySelectorAll('[data-ebay-selected-market-label]')).forEach(function (label) {
      label.textContent = selectedText;
    });
    Array.prototype.slice.call(section.querySelectorAll('[data-ebay-selected-market-flag], [data-ebay-trigger-market-flag]')).forEach(function (flag) {
      flag.className = flagClass(marketId);
    });
    Array.prototype.slice.call(section.querySelectorAll('[data-ebay-trigger-market-label]')).forEach(function (label) {
      label.textContent = selectedText;
    });
    Array.prototype.slice.call(section.querySelectorAll('[data-ebay-domain-label]')).forEach(function (label) {
      label.textContent = domainLabel(marketId);
    });
    Array.prototype.slice.call(section.querySelectorAll('[data-ebay-market-option]')).forEach(function (button) {
      button.setAttribute('aria-selected', button.getAttribute('data-ebay-market-option') === marketId ? 'true' : 'false');
    });
    Array.prototype.slice.call(section.querySelectorAll('[data-ebay-market-button]')).forEach(function (button) {
      var active = button.getAttribute('data-ebay-market-button') === marketId;
      button.setAttribute('aria-pressed', active ? 'true' : 'false');
    });
    section.setAttribute('data-ebay-selected-market', marketId);
    if (persist) {
      try { if (window.localStorage) localStorage.setItem('phoenix-ebay-market', marketId); } catch (err) {}
    }
    closeMenu(section);
  }
  sections.forEach(function (section) {
    if (section.getAttribute('data-ebay-localized-init') === '1') return;

    if (window.PhoenixAffiliateLocation && window.PhoenixAffiliateLocation.inferMarket) {
      marketId = window.PhoenixAffiliateLocation.inferMarket(available, {
        storageKey: 'phoenix-ebay-market',

      });

      marketId = available[0] || defaultMarket;
    }
    var select = section.querySelector('[data-ebay-market-select]');
    if (select) {
      select.addEventListener('change', function () {
        applyMarket(section, select.value, true);
      });
    }
    var trigger = section.querySelector('[data-ebay-market-trigger]');
    var menu = section.querySelector('[data-ebay-market-menu]');
    if (trigger && menu) {
      trigger.addEventListener('click', function (event) {
        event.stopPropagation();

        trigger.setAttribute('aria-expanded', expanded ? 'false' : 'true');

        if (picker) picker.classList.toggle('fr-ebay-market-picker--open', !expanded);
      });

        button.addEventListener('click', function (event) {
          event.stopPropagation();
          applyMarket(section, button.getAttribute('data-ebay-market-option'), true);
        });
      });
      document.addEventListener('click', function () { closeMenu(section); });
    }
    Array.prototype.slice.call(section.querySelectorAll('[data-ebay-market-button]')).forEach(function (button) {
      button.addEventListener('click', function () {
        applyMarket(section, button.getAttribute('data-ebay-market-button'), true);
      });
    });
    applyMarket(section, marketId, false);
  });
